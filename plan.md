# Cardora implementation plan

## Product outcomes

Build Cardora, a responsive VCF contact-collection platform. Authenticated owners create share links, select the countries allowed by the contact's phone calling code, set a hard contact limit, and receive an in-app alert when a link reaches capacity and stops accepting entries. Each link uses the owner's editable title/description/canonical URL for sharing metadata and the fixed Cardora brand image as its thumbnail. Public contributors provide only their name and international phone; email is optional and appears only when needed for email opt-in. Email and SMS preferences are separate, explicit, and revocable. Cardora account owners use email/password sign-up and sign-in for new accounts; email verification is not part of the selected initial flow.

Preserve the existing Open Ledger brand while fixing the observed narrow-screen dashboard overflow: use a working hamburger/drawer navigation on mobile, fluid layouts and tables, and a user-toggleable dark theme that persists across visits. Build a polished, detailed platform-admin dashboard that is visible only to users with the database `admin` role. It presents useful account, collection, consent and campaign health metrics without exposing individual public contributors' names, email addresses, or phone numbers.

SMS uses the user's configured Nena API key and sender identity `NENA.`. Only owners with valid, verified Kenyan (+254) numbers can see/use SMS management controls; SMS recipients must themselves have Kenyan (+254) numbers and explicit SMS consent. The user supplied one test number and asked for a flow test. Google Gmail OAuth remains per-owner, but its client credentials and production callback are to be configured on the user's production VPS; do not request or store Google credentials in Preview.

## Implementation approach

- **Stack and identity:** Continue the initialized React/TypeScript + Vite client, Express/tRPC backend and Drizzle/MySQL managed database. Replace Manus end-user OAuth with Cardora email/password sessions: new users sign up immediately, passwords are stored as scrypt hashes, and opaque random session tokens are stored only as SHA-256 digests. All owner operations remain scoped to the authenticated database owner ID. Reuse the existing admin-role guard for administrative reads. Keep per-owner Google Gmail OAuth separate; it is a notification integration, not Cardora account login.
- **Serving and deployment:** Keep the browser-rendered SPA plus Express APIs in the existing container. Public `/c/:slug` requests continue to receive server-rendered, per-link Open Graph/Twitter tags with the fixed Cardora image. Keep `/api/*`, the production-configured Google Gmail callback, health, share metadata, `/login`, `/privacy` and `/admin` routed before the SPA fallback as appropriate. Private profile, contact, campaign, admin, session and OAuth responses are `private, no-store`; public collection metadata stays uncached in Preview and must reflect current capacity. Do not publish or change the user's VPS.
- **Nena provider contract:** The user's [official Nena docs](https://www.nenasolutions.co.ke/api-docs) specify base URL `https://nenasolutions.co.ke/v1/api`, `Authorization: Bearer <token>`, `GET /sender-ids`, and `POST /sms/send`. The send body is `{ sender_id?: <active sender UUID>, to: <number|string|array>, message }`; `to` accepts an E.164 `+254…`, Kenyan `254…`, leading-zero local, or supported 9-digit local number, and one request supports at most 50 recipients. The send endpoint returns HTTP 201 even when `data.status` is `failed`, so success requires `status === "queued"` and canonicalized expected values in `data.accepted`. The sender field requires the active UUID, not the literal label: look up the active sender whose provider label/value is exactly `NENA.` and fail closed if it is not assigned. Never silently fall back to another sender ID. Respect provider credits (message segments × recipients), current consent and the API's 50-recipient batch limit.
- **Nena/OTP/security:** Keep `NENA_API_KEY` server-only and unchanged. Add time-limited one-time Kenyan owner phone verification, resend/attempt limits, keyed OTP digests (never store the code), and clear pending verification when the owner changes number. Mark the number verified only after the correct code is received and checked. Campaign sending requires the owner to be verified Kenyan, recalculates accepted/consented Kenyan recipients server-side, requires an explicit send action, records queued/failed/partial results, and never logs the token or unnecessary recipient data. The Nena API currently returns HTTP 403 to read-only `GET /wallet/balance` and `GET /sender-ids` from this development environment; do not attempt a live SMS send unless access becomes valid. Use mocked HTTP responses for deterministic tests and report the live-test blocker honestly.
- **Gmail:** Keep the selected per-owner Gmail OAuth architecture, but source `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `GOOGLE_REDIRECT_URI`, and `GMAIL_TOKEN_ENCRYPTION_KEY` from the user's production VPS environment only. Implement the server-side authorization-code flow with single-use state bound to the authenticated owner, PKCE, exact registered HTTPS callback, send-only Gmail scope plus identity scopes, exact connected-account identity, encrypted refresh-token storage, connection/disconnect status, and individual per-recipient messages with unsubscribe links. Preview has no Google credentials and must show that Gmail delivery is not yet connected; no email is claimed sent. Include a public `/privacy` page describing data access, storage, sending, and disconnection. Do not ask for or store VPS secrets in Web Dev configuration.
- **Admin dashboard:** Add read-only, admin-protected summary, user, collection and campaign views with pagination/search. Show platform totals, active/full/paused links, capacity use, country and opt-in breakdowns, provider readiness, recent signups/collections/campaigns and useful health/status cues. Do not show contributor-level contact PII, allow regular owners into `/admin`, or add destructive user/contact controls.
- **Responsive/theme design:** Retain the approved Open Ledger direction: warm paper, evergreen ink, sage, restrained citrus, editorial serif headings. Add a mobile top bar with a keyboard-accessible hamburger, backdrop, Escape/outside-close behavior and clear active section. Stack dashboard grids, keep tables intentionally horizontally scrollable without clipping the page, and make forms/dialogs fit viewport height. Add a persistent light/dark toggle and cohesive palettes for the landing, owner workspace, dialogs, public collection, privacy and admin pages; respect reduced motion and contrast.
- **Persistence:** Use additive, deterministic migrations for OTP records, campaign send/provider result fields, Gmail connection/state records, normalized email credentials and revocable opaque sessions. New sign-ups may not claim any existing OAuth-linked user row by email. Include an operator-run migration command that attaches a new password login to one exact existing account only when deliberately run against the production database; it preserves that row's role, ID, collections and contacts and refuses ambiguous matches. Preserve existing collection capacity transactions, contact consents, owner alerts and schema data.
- **Subscriptions and account quotas:** Add a default Free plan with a maximum of 100 accepted contacts across all collections and 5 retained collection links per owner; keep each collection's own configured contact cap in addition to these account-wide limits. Count every existing collection row toward the link cap; no delete/archive flow is added in this scope. Make plan definitions, quota limits, paid prices/currency/status, and user plan assignments editable only by admins; allow admins to assign and change a user's subscription without deleting account data. Owners see their current plan and account-wide usage. Enforce both account limits server-side, including concurrent public submissions, and reject further public entries across all of an owner's links when their account contact allowance is exhausted. If an admin lowers a plan below current usage, preserve existing data and stop additional growth until under limit.
- **Paystack manual renewals:** The user selected Paystack for production and manual renewal for both card and Kenyan M-PESA. Implement one-time hosted KES checkout with the `card` and `mobile_money` channels; do not use a Paystack plan code, automatic renewals, reusable payment authorizations or stored card details. Initialize transactions server-side, verify the transaction on return, and validate HMAC-SHA512 over the exact raw webhook body; activate or renew access only after the verified reference, success status, exact amount and KES currency match. Process successful-charge webhooks idempotently. Require `PAYSTACK_SECRET_KEY` and an explicit HTTPS `CARDORA_APP_URL` only on the production VPS. Keep checkout unavailable in Preview; do not request/store a live key here, make live charges, publish, or deploy to the VPS in this change.
- **Current subscription boundary:** The additive plans/assignment/payment schema, admin-managed tier editor and manual account assignment, owner plan/usage/checkout state, default Free quotas, and account-wide server enforcement belong in this implementation. Checkout must make a one-time payment for a paid-through term and require a new manual payment at renewal; do not imply a purchase or access grant until the server verifies it.
- **Sharing and VCF:** Keep country validation based on `libphonenumber-js` calling codes; reject invalid, duplicate, disallowed-country, closed and over-capacity submissions. Generate VCF 3.0 server-side with CR/LF-safe escaping. Keep the user-provided URL constrained to `/c/<slug>` and descriptions escaped in social metadata.

## Provider research and current setup

The prior TextSMS choice is superseded. Nena's [official API docs](https://www.nenasolutions.co.ke/api-docs) document the bearer-authenticated endpoints and exact SMS request semantics above; `GET /sender-ids` returns active sender UUIDs and display fields. The project config confirms `NENA_API_KEY` is already configured for all environments. Read-only calls to both Nena wallet-balance and sender-ID endpoints returned HTTP 403 from this development environment, so the requested live SMS test remains blocked and no message was sent. Google's [Gmail OAuth server flow](https://developers.google.com/workspace/gmail/api/auth/web-server), [send guide](https://developers.google.com/workspace/gmail/api/guides/sending), and [scope reference](https://developers.google.com/workspace/gmail/api/auth/scopes) inform the production-VPS OAuth implementation; Google credentials are not collected in Preview.


## Independent-review refinements

- **Trusted canonical URLs:** The saved `/c/<slug>` URL must use the current browser-facing Cardora origin or an exact HTTPS origin explicitly listed in the production server's comma-separated `CARDORA_PUBLIC_ORIGINS` environment variable. The list is an operator assertion that each alternate origin serves this Cardora deployment; arbitrary HTTPS hosts are rejected. Do not derive social URLs from Express's internal `Host`.
- **Snapshot-bound campaign review:** Preparing a draft selects the exact currently eligible recipient identities/destinations, displays that set to the owner, and persists a SHA-256 digest bound to the channel, subject, message, contact IDs, names, and destinations. The explicit send confirmation carries a server-issued review digest bound to the stored campaign and recipient snapshot. Immediately before provider I/O, the server re-queries current eligible recipients and compares the complete digest; if it changed, no provider request is made and the owner must save and review a fresh draft.
- **Searchable administration:** Account, collection and campaign tables all support server-side search while retaining pagination. Collection search includes title/slug/status and owner identity; campaign search includes subject/channel/status, owner and collection references. Contributor-level contact PII remains excluded.
- **Privacy disclosure:** The public page states that Gmail refresh tokens are encrypted at rest, and that disconnect removes the stored token and revokes access where supported.
- **Subscription administration integrity:** Preserve stored `past_due`, `canceled` and `expired` assignment states in owner/admin readback while falling back to Free entitlements when the assignment is no longer usable; show active assignments past their end date as expired. Because Paystack renewals are one-time/manual (not provider subscriptions), admins may immediately override a paid-through assignment. Block plan assignment/deactivation only while an unresolved checkout is initializing or pending, and serialize default-plan switches by locking the current default row inside the transaction.

## Email account authentication replacement (user-selected)

- Remove Manus OAuth as Cardora's end-user sign-in: remove its callback route, login UI/helper, preview sessionStorage/Bearer fallback, and browser-exposed OAuth portal settings. Keep unrelated Manus platform API configuration only where an existing feature such as Maps needs it, and keep the separate per-owner Google Gmail consent flow.
- Provide email/password registration and sign-in for new accounts. There is no email verification or password-reset email in this selected initial flow; the form and privacy disclosure must not imply otherwise. Validate email/password on the server, hash passwords with Node's scrypt, rate-limit login/sign-up attempts, and store opaque revocable server-side sessions rather than raw passwords/tokens in the browser.
- Legacy OAuth-linked accounts are not claimed by entering their email in sign-up and their rows/data/roles remain untouched. The deliberate `pnpm exec tsx scripts/migrate-legacy-email-account.ts` operator tool attaches a new password login to one exact existing account only when run manually on the VPS; it refuses missing/ambiguous accounts and never changes role or transfers data.
- CSRF-protect tRPC mutations using a host-only double-submit token and send cookies with secure attributes compatible with the HTTPS Preview proxy. Preserve the `/login` route in the source and origin-root route manifest.
